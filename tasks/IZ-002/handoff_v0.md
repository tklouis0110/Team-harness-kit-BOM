# v0 向け handoff — BOM キャンバス画面（IZ-002）

この文書は、Vercel v0 で「画面」を作るための仕様・機能のまとめです。
**API とデータ（SQLite・GitHub への保存）はもうあります。v0 に作ってもらうのは画面だけ**です。
例の値はすべて作り物です（実データは入れていません）。

---

## 1. 何のための画面か（1 分で）

- 会社の製品を「**商品グループ**」に分け、グループごとに「**品番**」をぶら下げて見る、大きなホワイトボード（キャンバス）。
- 品番ごとに、**工程（Routing）**＝作る順番（見るだけ）と、**BOM（部品表）**＝使う部品の表（編集できる）を持つ。
- 使う人は非エンジニア（製造・生産管理）。専門用語を避け、日本語の画面にする。
- 規模: **グループ 76・品番 1032**（画面で足すと増える）。ファミリー 9 列（シングル・ハイブリッド・モリブデン・電鋳・ミラーブラック・その他・フイルム・型・金属材料）。

### 言葉の決まり（画面の文言に必ず守る）

| 言葉 | 意味 | 注意 |
|---|---|---|
| **アイテム** | BOM に入る**部品**（材料・消耗品など。数量・単位を持つ） | 工程を「アイテム」と呼ばない |
| **工程** | 作る順番（Routing）。IZ-001 から作った、**見るだけ** | 画面から編集するボタンを置かない |
| **BOM** | 品番ごとの部品の行の表 | 編集できるのはここだけ |
| **注記** | IZ-001 で仮定のまま進めた箇所の説明（赤系で目立たせる） | 畳んで隠さない（後述の「畳み」の扱いを参照） |

## 2. 一番困っていること（直してほしい点）

人が実際に触って出た声（2026-11-26）。**優先順に並べました。**

1. **何より、BOM の構造・グループが視覚的に見えない。**
   グループの塊、グループ→品番の親子、品番の「工程 n・部品 m」が、一目で分かる画面にする。
2. **上の帯が大きい。** 全体の注記・警告・入力欄で画面が狭くなる。
3. **右のパネルが見づらい。** 注記が多くて本題（BOM の編集）に届かない。工程と BOM が混ざる。
4. **追加・編集の手順が分かりにくい。** 新規アイテム → 新規品番 → BOM の行、と画面を行き来する。
5. **キャンバスの操作。** 1032 品番が並ぶので、探す・全体に戻す・畳むが欲しい。

## 3. 画面に必要な機能

### 3.1 キャンバス（ホワイトボード）— 主役

- 列 = ファミリー。列の順は API が決める順（§5.1 のとおりグループの並び順の最小値の順）。
- 列の中に**グループのブロック**を縦に並べる。ブロック = 見出し（グループ ID・前工程G／後工程G・品番数・工程の流れ）＋**品番の行**（親子の線でつなぐ）。
- 品番の行に「**工程 n・部品 m**」を出す。判定が `要確認` は赤系、`類推` は橙系の背景。
- 注記があるグループ・品番には**印**（例 `! 2`）を出す。
- 操作: ドラッグで動かす、ホイールで拡大・縮小、最初は全体が入る倍率、**「全体に戻す」ボタン**。
- あると良い（今のものに無い。画面側の機能として足してよい）: グループ ID・製品名・品番 ID の**検索**／グループを**畳む・展開**／ファミリーごとの**色分け**。
- ブロックどうしは重ならない。
- グループ・品番を押すと、右のパネルが開く。

### 3.2 右のパネル（詳細）

- **グループを押したとき**: グループの値（ファミリー・前工程G・後工程G・区分・特徴・工程の流れ）→ 注記 → 品番の一覧（押すとその品番へ）。
- **品番を押したとき**（タブ切り替えを推奨。ただし**注記は必ず目に入る**ようにする）:
  1. 品番の見出し（製品名・品番 ID・ファミリー・グループ・判定）
  2. **注記**（品番の注記、そのグループの注記）— 常に見える
  3. **BOM（部品）** — 編集の中心。追加・変更・上へ/下へ・削除
  4. **工程（Routing）** — 見るだけ。行ごとに注記（日報Map の要確認）が付くことがある
- BOM が空のときは「部品はまだありません」。部品（アイテム）がまだ 1 つも無いときは「先に新規アイテムを追加してください」。

### 3.3 追加・編集（すべて 1 操作ごとに保存）

| 操作 | 画面 |
|---|---|
| 新規アイテム（部品） | 種別（自由入力・1〜20 字）・コード（1〜40 字）・名前（1〜100 字） |
| 新規品番 | グループを選ぶ・製品名（1〜100 字。既存と同じ名前は不可）。工程も BOM も空で作られる |
| BOM に行を足す | アイテムを選ぶ・数量（0 より大きい）・単位（1〜20 字）・位置（空 = 末尾） |
| BOM の行を変える | 部品・数量・単位 |
| BOM の行を動かす | 上へ／下へ（位置の指定でもよい） |
| BOM の行を消す | 確認のあと削除 |

- 「品番を追加したら、そのまま BOM の行を足せる」流れにする（手順の行き来を減らす）。
- **変えられないもの**: グループ・工程・注記・既存の品番とアイテム（名前・種別の変更やグループの付け替えも無い）。削除できるのは BOM の行だけ。
- 操作中（送信中）は、編集のボタンを押せなくする。

### 3.4 上の帯（できるだけ小さく）

- 数字の要約: `グループ 76・品番 1032（IZ-001 分 1032・画面で追加 0）・アイテム（部品）0・BOM の行 0`
- 次の 1 文を常に表示する: **「同時に編集すると、後から保存した人の操作は保存されません（読み込み直してやり直す）。」**
- 全体の注記（`global_notes`。§5.2）。
  - 今の仕様は「**畳まない**（編集する人が必ず目にする）」です。
  - ただし帯が大きいのが困りごとなので、**常に見えたまま高さを抑える**（例: 横に並べる、細い帯、アイコン＋ホバーではなく**常時表示の 1 行ずつ**）形を提案してください。畳んで隠す案を出す場合は、別案として分けて出してください（仕様の変更になるため、人が決めます）。
- 「読み込み直す」ボタン。

### 3.5 エラーと同時編集（必ず守る挙動）

- 保存は**操作 1 つごとにすぐ送る**。送るとき、画面が**最後に読んだ版**（`base_version`）を付ける。
- 成功（200）→ 版を新しくし、キャンバスと開いているパネルを**読み直す**。
- **409（衝突）→ 次の文をそのまま出す**: 「**他の人が先に保存しました。読み込み直してからやり直してください**」。**自動で送り直さない。**「読み込み直す」ボタンを出す。
- 400 → サーバの `error`（日本語）をそのまま出す。
- 502（GitHub に保存できなかった）→ `error` を出す。
- 同時に使う人が多いと 409 が増える仕様です（方式の弱点。人が了承済み）。

## 4. 画面の見た目

- 文字は日本語。フォントは Noto Sans JP、数字は Arial 風でよい。
- 色（会社の様式）: 黒帯 `#121A16`（白文字）、文字 `#262626`、補助の文字・線 `#5C7066`、見出しの背景 `#eef1ef`、強調 `#23CC68`、淡い緑 `#DEF7E8`。
- 注記は赤系（左に太い線＋薄い赤の背景）、判定 `要確認` は赤系・`類推` は橙系（色だけに頼らず文字でも示す）。
- 余白は詰め気味でよい（業務ツール）。スマホは対象外（PC のブラウザ）。
- 外部のライブラリ・ビルドの道具は、v0 の標準（React・Tailwind・shadcn/ui）なら使ってよい。**ただしデータの取得は §5 の API だけ**。

## 5. API（すでにある。変えない）

ベース URL は同じオリジンの `/api/...`。すべて UTF-8 の JSON（`canvas.svg` だけ SVG）。

### 5.1 読み取り

| 呼び方 | 返すもの |
|---|---|
| `GET /api/meta` | `{ version, counts: {groups, products, products_iz001, products_web, routing_steps, items, bom_lines}, global_notes: [{kind, target_id, text}] }` |
| `GET /api/canvas.svg` | キャンバスの SVG（`data-version` に版）。**今の画面はこれを埋め込んでいる** |
| `GET /api/group?id=<group_id>` | `{ version, group: {group_id, family, front_g, front_section, front_feature, back_g, back_section, group_flow}, notes: [{kind, text}], products: [{product_id, product_name, judge}] }`（品番は並び順） |
| `GET /api/product?id=<product_id>` | `{ version, product: {product_id, product_name, family, group_id, judge, origin}, notes: [{kind, text}], group_notes: [{kind, text}], routing: [{seq, process_code, name, src_key, notes: [{kind, text}]}], bom: [{line_id, seq, item_code, item_type, name, qty, unit}] }`。無い id は 404 |
| `GET /api/items` | `{ version, items: [{item_code, item_type, name, origin}] }`（部品だけ。工程は入らない） |

**重要（キャンバスを v0 で作り直すとき）**: 今の API には「**全グループ・全品番を 1 回で返す一覧**」がありません。
- 方法 A（API を変えずに）: `/api/canvas.svg` を取得して、中の `g.group[data-group-id]`・`g.product[data-product-id][data-routing-n][data-bom-n]`・`g.note-mark[data-n]` を読む。
- 方法 B: `/api/group` を 76 回呼ぶ（重い）。
- 方法 C（推奨・要承認）: 読み取り専用の `GET /api/tree`（全グループと全品番とその数・注記の数・判定を 1 回で返す）を**足す**。API の追加は仕様の変更なので、**v0 の作業とは別に、人が決めてから**私（Claude Code）が足します。v0 では C を前提にせず、まず A か「モックデータ」で作り、C が入ったら差し替えられる作りにしてください（データ取得を 1 か所にまとめる）。

### 5.2 注記の種類（kind → 画面の表示名）

| kind | 表示名 | どこに付くか |
|---|---|---|
| `scope` | 対象範囲 | 全体 |
| `template_match` | お手本との照合 | 全体（ファミリーごと） |
| `new_g` | 新しい G | グループ |
| `unentered` | 工程未入力 | グループ |
| `no_nippo_code` | 日報コードなし | グループ |
| `check_products` | 要確認の品番 | グループ |
| `judge` | IZ-001 の判定 | 品番 |
| `template_diff` | お手本と違う | 品番 |
| `map_check` | 日報Map 要確認 | 工程の行 |

### 5.3 編集 `POST /api/edit`

本文: `{ "op": "<操作>", "base_version": "<最後に読んだ版>", ...入力 }`

| op | 入力 | 200 で返す（`ok: true`, `version` に加えて） | 400 になる主な場合 |
|---|---|---|---|
| `add_item` | `item_type`, `code`, `name` | `item_code` | 空・長すぎ・コードの重複 |
| `add_product` | `product_name`, `group_id` | `product_id`（例 `W0001`） | 空・既存と同じ製品名・無いグループ |
| `add_line` | `product_id`, `item_code`, `qty`, `unit`, `position`（省略可） | `line_id` | 無い品番/アイテム・数量が 0 以下か無い・単位が空・位置が範囲外 |
| `update_line` | `line_id`, 変えるものだけ（`item_code`/`qty`/`unit`） | `line_id` | 無い行・数量 0/null・単位が空・無いアイテム |
| `move_line` | `line_id`, `position` | `line_id` | 無い行・範囲外の位置 |
| `delete_line` | `line_id` | `line_id` | 無い行 |

- 失敗: `{ "ok": false, "error": "<日本語の理由>" }`。衝突: **409** `{ ok: false, error: "conflict", version: "<今の版>" }`。
- 工程を変える操作は**ありません**（送っても 400）。

### 5.4 版（version）

- DB ファイルの中身から計算した指紋。中身が変わると変わる。**画面は読んだ版を覚え、編集のたびに `base_version` に付ける。**

## 7. 渡し方・つなぎ方

- v0 では、上の §5 の形のモックで画面を作る（モックは 1 か所に集める）。
- できた画面（React）は、このリポジトリの `tasks/IZ-002/src/web/` に置き直す前提です。**どう置くか（今の素の HTML/JS を React に差し替えるか、Vercel 側に別プロジェクトとして置くか）は、人が決めます。**
  - 今のサーバ（`src/serve_local.py`）は、素の HTML と JavaScript だけを配ります。React をビルドして動かすには、ビルドの道具が要ります（現在の仕様は「外部のライブラリ・ビルドの道具を使わない」）。**これは仕様の変更になるので、v0 の成果を取り込む前に、人が決めて再ロックします。**
  - 取り込むときは Claude Code が行います（API・DB・検査は変えない）。
- 実際の Vercel への公開（環境変数・閲覧と編集の制限・保存のたびの再デプロイを止める設定）は **IZ-003**（別タスク）です。
- v0 に渡さないもの: 実データ（品番・製品名・顧客名）、GitHub のトークン、`.env`。
